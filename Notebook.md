# Entry 1: Design Notes
I like where this is going and it seems to be fleshing out like how I had it in my mind which I am pleased with. However, the more I think about it, I am worried that the OBO feature is going to be very complicated to implement. Thus I think it will be best to implement standard buying and selling first and if I have time, only then will I implement the OBO feature. In terms of design choices, I stayed pretty true to my original problem framing (the only part of that that I changed was to find more concrete evidence of the bad situations I was describing) and most of the innovation for this step came from the concept and reaction specifications.

The approved alpha scope is fixed-price listing, claiming, buyer payment reporting, seller receipt confirmation, and sold status. OBO, messaging, and claim cancellation are deferred. Concepts remain independent and application reactions connect them. Figma templates are visual references; detailed styling will be refined with the project owner.


## Entry 3: Accounts and marketplace increments — October 13, 2026

MongoDB's container responds successfully to ping. Authentication and Sessioning were adapted from the framework's message-board example to persist in independent MongoDB collections. Authentication uses Argon2id hashes with unique usernames; sessions use opaque IDs and expiry checks with a TTL index. HTTP-only cookies are supplied by the framework's HTTP adapter. Integration tests verify duplicate registration, wrong passwords, persistence after concept reconstruction, expiry, and sign-out.

The fixed-price alpha implements Listing, Claiming, and TransactionConfirming. Listing details are validated JSON text containing title, description, price, category, pickup, payment instructions, and an optional image URL. This is an implementation simplification over separate state fields in P1. Listing editing/removal and release are deferred. Claiming uses an atomic conditional MongoDB update and a unique resource index. Reactions make listings available, start transactions with the listing instance as subject, and complete claims after receipt confirmation. A purchase-policy view prevents self-claims. Payment actions enforce the payer/payee inside their independent concept.

An API journey test starts empty, creates separate accounts, publishes, races two claims, checks unauthorized actions, reports payment, confirms receipt, and checks sold status after application reconstruction. Initial testing passed, but browser testing revealed that a required transaction read hid unclaimed listings. Replacing it with `whether` preserves rows with null transaction fields. The journey test now explicitly verifies that a newly published, unclaimed listing is visible. This changed the validation plan: intermediate browse states are tested, rather than only the final sold state.

The Vue interface uses generated HTTP client types. Its visual direction is warm cream, terracotta, and sage, with an original CSS furniture illustration and spacious item cards. Figma references were not copied literally. Search, categories, Buying/Selling views, item details, and forms support the core journey. Mutations refresh state immediately, while three-second polling reflects actions from another session. Informative errors surface in the relevant dialog. The recording outline and P3 scope are in ALPHA.md. Account membership verification and cross-concept crash recovery remain future work.

Browser verification completed the full journey using demo_sophia and demo_percy and a clearly labeled demonstration chair, without any real payment. The chair progressed through Available, Reserved, Payment sent, and Sold without refreshing. The completed sale was visually verified. Framework checking reports nine MISSING_ENDPOINT_FALLBACK advisories (including the framework's copied session composition) and a source-order-sensitive former information advisory. The API tests cover admitted success and refusal branches; these advisories are retained as an alpha limitation rather than claimed to be eliminated. Vue typechecking and the production build pass.

Final automated validation: six tests pass with 47 assertions, including a test suite for each implemented concept and the complete API journey. The responsive viewport check reported no horizontal document overflow at phone width; the browser viewport was restored. Recording with personal narration remains to be completed by the project owner using the supplied script.

## Entry 4: Cancellation and interface revision — October 13, 2026

The project owner requested cancellation and a visual redesign after rejecting the initial appearance. Cancellation extends the alpha scope: an unpaid transaction may be atomically deleted by its payer, and a reaction then releases that payer's claim. A fresh buyer can claim the available item and start a new transaction. Cancellation after reporting payment or after confirmation is refused. Atomic deletion races safely with the conditional payment update: exactly one succeeds. This adds cancel to TransactionConfirming and release to Claiming; the original Design folder is unchanged. Seven tests pass with 64 assertions, including cancellation/reclaiming, payment/cancellation races, forged session input rejection, and cross-origin request rejection.

Usability fixes include dialog focus management and Escape dismissal, inert background content, failed-image fallbacks, active filter semantics, a visible sale progress indicator, resetting filters after publication, and retaining the last saved state with a reconnect notice when polling fails. Listing queries explicitly use creation order. The implementation prevents overlapping polling requests and stale loads from repopulating a signed-out account.

The owner clarified that both buyer and seller should be able to cancel unpaid reservations. TransactionConfirming.cancel now accepts an actor and atomically checks that actor against either participant. It returns the original payer so the reaction releases the correct claim even when the seller cancels. The API test now verifies seller cancellation as well as buyer cancellation and rejects cancellation after payment is reported.

The owner requested an eBay-like structure with cleaner styling and spacious individual item pages, rather than cramped marketplace cards. The redesign uses white, charcoal, subtle gray accents, narrow corner radii, open listing rows, and a compact header. Listing links open dedicated /items/<id> pages with a large image area, description, seller/pickup details, and payment progress. History navigation, direct URLs, and page refreshes are supported; My activity has /activity. Original design documents remain untouched. Browser verification confirmed a dedicated item page survives a direct refresh. The marketplace and item-page layouts were visually verified.

Validation for this revision: seven tests pass with 66 assertions; backend specification/artifact/type checks, Vue typechecking, and production build pass. The framework retains conservative endpoint fallback advisories. Browser checks confirmed item links, direct refresh, and navigation back to the marketplace. Both listing and item layouts have no horizontal overflow at the phone viewport; the viewport was restored after testing. Existing user-created listings were preserved.

## Entry 6: Photo uploads — October 13, 2026

The owner requested file uploads instead of an image URL field. A new independent ImageUploading concept stores images on local disk. Its endpoint authenticates the session before accepting a photo through the generated typed API. JPEG, PNG, and WebP inputs are decoded and checked against their declared format, limited to 5 MB and 25 million pixels, oriented, resized to fit 1600 by 1600, and encoded as WebP without original metadata. Fresh generated filenames are served by the HTTP host; original filenames never become filesystem paths. Listing accepts these generated relative URLs while retaining compatibility with earlier image URLs.

The form now offers a file picker, local preview, replacement, and removal. Upload occurs when publishing; a successful upload is reused if publishing must be retried, and the chosen file remains available after an error. Local uploads persist across rebuilds and server restarts and are ignored by Git. Unused uploads are not yet garbage-collected. This replaces the earlier decision to defer image uploads; Design remains unchanged.

Validation: eight tests passed with 78 assertions, including image content/type/size validation, resizing, authenticated upload, and publishing a listing with its uploaded image URL. Vue typechecking, framework/artifact/backend checks, and the production build passed. Browser verification selected a local JPEG, displayed its preview and filename, and removed it successfully without publishing a test listing. Additional large-file and image-serving/path tests were added afterwards, but their execution request was declined; those additional checks remain unverified. The running server uses the equivalent inline image-serving implementation verified by code inspection; the source now extracts that behavior into image-host.ts for testing.

The owner requested a grid instead of line items, public browsing, and seller-created tags instead of a category navigation bar. Guests can browse descriptions, photos, tags, and availability without signing in; clicking Claim opens authentication on the same item page. Publishing, uploading, claiming, payment actions, cancellation, and private activity continue to require authentication. Listing metadata now includes up to 12 normalized tags, each at most 40 characters. Sellers can search a broad suggestion catalog, select tags, or create custom tags. Published custom tags are stored with the listing and become available as suggestions and filters. Older category-based listings remain usable through a category-to-tag fallback. Keyword search matches title, description, pickup, and tags; selected tags all must match. The Filters panel combines tag selection, availability, and minimum/maximum price. The category bar and seller category dropdown were replaced.

## Entry 9: Clothing-size filtering — October 15, 2026

Follow-up: clothing size is an optional restriction, not a requirement that every matching listing have a size. With XL selected, items without a clothing size still pass the size check; explicitly sized items must match XL. Keyword, tag, availability, and price filters continue to apply. This keeps unsized bikes visible when searching for bike with XL selected. A regression test covers unsized bikes, matching/mismatching jerseys, and keyword filtering.
